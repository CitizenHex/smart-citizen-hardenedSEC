# Smart Citizen 1.3.1 — Critical Fixes, Faster Extraction, Mission BP Catch-Up

> ⚠️ **Heads-up if Windows blocks the installer:** Smart Citizen is not yet code-signed, and Windows 11's **Smart App Control** (SAC) blocks unsigned installers — Properties → Unblock does **not** help with SAC. To install:
>
> 1. Open **Settings → Privacy & security → Windows Security → App & browser control**.
> 2. Click **Smart App Control settings** and set it to **Off**.
> 3. Run `SmartCitizen-1.3.1-Setup.exe` and finish installation.
> 4. After install, you can return to the same screen and turn Smart App Control back on if you'd like.

---

## Headline

**If you're on 1.3.0, install this.** Two critical bugs are fixed: DataForge extraction crashed on every attempt in the standalone build, and `user.ini` could be truncated to zero bytes on close after a load mismatch. On top of that, this release ships a major DataForge extraction speedup (parallel unp4k + an XML diff cache that skips regenerating unchanged enhancement categories), a watermark on the in-game main-menu version chip so it's visible Smart Citizen is active, and the **Mission Blueprint Coverage Catch-Up** that surfaces ~1,400 newly-eligible `[BP]` / `[BP?]` tags from the PTU patch.

## Critical fixes

### DataForge extraction crashed in v1.3.0 (Python 3.11 standalone)

`shutil.rmtree`'s `onexc=` callback keyword was added in Python 3.12. The hardening that landed in v1.3.0 used it unconditionally, and the frozen build runs on Python 3.11 — so every DataForge extraction in the standalone v1.3.0 build crashed with:

```
DataForge extraction failed: rmtree() got an unexpected keyword argument 'onexc'
```

1.3.1 picks the right kwarg (`onerror` on 3.11, `onexc` on 3.12+) based on the Python version at import time, with a callback signature that's compatible with both.

### user.ini could be erased to zero bytes on close

When the app closed without successfully loading entries (or after a load-mismatch scenario), the close-time autosave could write an empty `user.ini` over the populated one on disk — silently destroying every custom value you'd saved. A user reported this happening after installing v1.3.0 on a second machine.

1.3.1 adds a guard: the autosave refuses to write if there are zero modified entries AND a non-empty `user.ini` already exists on disk. If you've ever seen a 0-byte `user.ini` after closing the app, that path is now defended.

### Some components showed stock text in-game with no stats / class tag

CIG ships a handful of components — the **S3 QDRVs Agni, Vesta, Fissure, and Impulse** on PTU 4.8 — with two loc keys for the same item: `item_DescX` and `item_DescX_SCItem`. The enhancement generator only emitted enhancements for the `_SCItem` variant. The game can render either, so depending on which key the in-game UI hit, you'd see the full enhanced description on some components and stock text with no `--- STATS ---` block (and no `[CLASS-Sx-grade]` name tag) on others.

1.3.1 mirrors enhancements onto the bare-key sibling when stock ships both. After re-extracting, all four QDRVs (and any future components with the same dual-key pattern) get their annotations regardless of which key the game decides to render.

### user.cfg gained a duplicate `g_language = english` line on every Apply

The existing-setting check was a literal string match against `"g_language = english"` — any non-canonical formatting (no spaces, mixed case, quoted value, trailing comment) looked like "missing" and appended a second canonical line on every Apply to Game. Over many applies users could accumulate many duplicate entries.

1.3.1 uses a case-insensitive regex that recognizes any spacing, casing, or quoting variant. If the key is present at all, the file is left untouched. If it's set to something other than `english` the value is logged but **not** silently overwritten — we don't change a deliberate non-English locale choice.

## Performance & UX

### DataForge XML diff cache

Re-extracting from `Data.p4k` no longer regenerates every enhancement category from scratch. A SHA-256 manifest of the cached DataForge XMLs is written after each extraction; on the next run, only the categories whose source XMLs actually changed are re-run. In practice, after the first full extraction, re-extractions skip the bulk of the generator work.

- mtime is checked first as a fast pre-filter; content hashes confirm before flagging dirty.
- Manifest lives next to the cache as `.diff_manifest.json` — delete it to force a full regen.
- Categories tracked: ships, components, ship_weapons, fps_weapons, missions, commodities, journal.

### Parallel unp4k + faster unforge

Smart Citizen now bundles a fork of **dolkensp/unp4k** ([Osiris-DevWorks/odw-fast-unp4k](https://github.com/Osiris-DevWorks/odw-fast-unp4k)) with parallel decompression of the p4k entries and substantially faster DataForge → XML conversion. End-to-end DataForge extraction is noticeably quicker on every machine and dramatically faster on multi-core ones.

### DataForge cache moved off OneDrive-synced Documents

The DataForge XML cache (~1 GB) used to live under `Documents\Smart Citizen\<channel>\cache\dataforge\`. When Documents is OneDrive-synced, every extraction triggered hours of background uploads and made re-extracts slow because Windows had a thumb on every file-open. The cache now lives at `%LOCALAPPDATA%\Smart Citizen\<channel>\cache\dataforge\` (default, falls back gracefully if `LOCALAPPDATA` is unset). One-shot migration runs on first launch.

Your `user.ini`, backups, and per-channel preferences still live under `Documents\Smart Citizen\` — the move only affects the bulk XML cache.

### Snapshot phase now parallelized and shows progress

The post-extraction SHA-256 sweep over ~28k XML files (used to build the diff manifest) used to run serially with no progress reporting — so the app appeared frozen for the duration. 1.3.1 parallelizes the hash sweep with a thread pool (I/O-bound on Windows because of Defender / Search Indexer / OneDrive intercepts) and reports `(completed/total)` to the progress bar throughout.

### Progress dialog stays continuous through the pipeline

Previously the DataForge Extraction dialog closed and a separate Generating Enhancements dialog opened, leaving a visible gap where users wondered what was happening. 1.3.1 hands the dialog window off between phases — the title and label change, but the window stays on screen continuously.

### Config tab paths show in native Windows format

After clicking *Browse*, the install root and Smart Citizen Data fields showed forward-slash paths (`C:/Games/...`) because `QFileDialog` returns POSIX-style separators on Windows. The fields now always display backslashes regardless of how the path arrived — installer, browse, or manual edit.

## New features

### Main-menu version watermark

Apply to Game now stamps the stock `Frontend_PU_Version` value with `| Localizations Enhanced with Smart Citizen vX.Y.Z`. The game shows that string verbatim on the main menu, so it's visible at a glance (and in screenshots / support tickets) that customizations are active.

Idempotent across re-applies: a prior watermark — current phrasing or either of the prereleased variants — is stripped before re-appending the current one, so successive applies and version bumps don't accumulate suffixes.

## Mission Blueprint Coverage Catch-Up

The PTU patch landed a **massive blueprint expansion** for missions: roughly 1,400 new `<BlueprintRewards>` references across hauling, courier, mercenary, mining, refueling, and Foxwell-defend mission families. Smart Citizen's mission scanner was looking in only one of CIG's blueprint-pool directories and missed almost all of it — `[BP]` / `[BP?]` tags weren't showing up on the new BP-paying missions even though the data was sitting in the cache.

This release fixes the scanner so the next DataForge extraction surfaces the full picture.

**Specific mission families that gain BP coverage after re-extracting:**

| Family | What changes |
|---|---|
| **`UWC_Refueling_*`** (United Wayfarers Club) | 5 brand-new refueling missions, all gain `[BP?]` tags pointing at the new `bp_rewards_fuelnozzle.xml` pool. Reward category: `crafting/blueprints/crafting/vehiclegear/refuelling/nozzle/`. |
| **Hauling** (`Covalex_*`, `Redwind_*`, `LingFamily_*`) | Three hauling generators picked up BP refs (48 / 54 / 21). `Covalex_HaulCargo_*`, `Redwind_*`, `LingFamily_Hauling_*` titles all eligible. |
| **Courier** (`FTL_Courier_*`) | 78 new BP refs. |
| **Mercenary** (`Eckhart`, `Foxwell`, `Headhunters`, `Intersec`) | Eckhart escort/ambush/killNPC, Foxwell defend-entities, Headhunters defend-entities + mercenary-ship contracts all gain BP refs. |
| **`Shubin_*` ship mining** | Largest single-file gain at **+573 BP references** — a new tier of mining-mission blueprint rewards. |
| **`Adagio_*` ship salvage** | New BP coverage. |
| **`TheCollector_*` (Wikelo)** | +10 BP refs. |
| **`Foxwell_X2_*`** (XenoThreat 2 finale missions) | New BP rewards via `xenothreat2rewards/` pools. |

After installing 1.3.1, click **Extract from Data.p4k** on the PTU channel (or any channel that's been patched) to rebuild the cache against the corrected scanner. The `mission_rewards_enhancements.ini` will gain `[BP]` / `[BP?]` tags + structured *POTENTIAL BLUEPRINTS* blocks on dozens of newly-eligible mission titles.

## New diagnostic tool

- **`scripts/diff_mission_rewards_channels.py`** — diffs `mission_rewards_enhancements.ini` between any two SC channels (LIVE vs PTU is the typical use). Surfaces:
  - Missions present in both channels whose title gained a `[BP]` / `[BP?]` tag in B
  - Brand-new mission titles in B, split by whether they carry a BP tag
  - BP tags that were removed (regression watch)
  - Categorized by mission family for readability

  Usage: `python scripts/diff_mission_rewards_channels.py LIVE PTU --out diff.md`

  Useful for every PTU patch going forward — quickly see what blueprint coverage CIG added or moved.
